# S6. jt400 (JTOpen) contra PUB400 — mecánica de conexión

Fecha: 2026-10-14. Origen: VPS de desarrollo (Linux, Java 21.0.12, Maven 3.9.9). Destino: PUB400.COM (IBM i público, Alemania). RTT medido con ping: **~112 ms**.

**Veredicto: confirmado.** jt400 21.0.7 (clasificador `java11`) desde Java 21 hace signon, detecta la contraseña expirada, la cambia por API, abre JDBC con TLS y sin TLS y ejecuta consultas parametrizadas con `naming=sql`. Las latencias están dominadas por el RTT de este VPS; en el Banco (misma red o VNet con ExpressRoute) van a ser mucho menores, pero la **proporción** (conectar cuesta ~30 veces una consulta) se mantiene, y eso alcanza para decidir que hace falta un pool.

## Hipótesis

Una Function Java 21 puede llegar a un IBM i con jt400 (JDBC tipo 4) usando la misma URL que `ResolutorClienteJt400` (`jdbc:as400://host;prompt=false;naming=sql;secure=...`), con TLS, manejar la contraseña expirada del perfil y obtener latencias que permitan resolver un cliente por solicitud.

## Cómo se ejecutó

Proyecto Maven aparte en `spikes/s6-jt400/` (no toca `function/`): dependencia `net.sf.jt400:jt400:21.0.7:java11` (la misma de `function/pom.xml`, resuelve sin problemas) más Jackson para leer/escribir `local.settings.json`. Clase única `spike.SpikeJt400`. Las credenciales se leen de `function/local.settings.json` (`AS400_HOST`, `AS400_USER`, `AS400_PASSWORD`); la salida pasa por un filtro que reemplaza usuario y contraseña por `<USER>` / `<PWD>`.

Re-ejecutar:

```bash
bash spikes/s6-jt400/correr.sh                      # usa function/local.settings.json
bash spikes/s6-jt400/correr.sh /ruta/a/otro.json    # u otro archivo con el mismo formato
```

## Signon y contraseña expirada

- `SecureAS400` (TLS, 9476) con la contraseña inicial → `AS400SecurityException` **rc=7 (`PASSWORD_EXPIRED`)**, texto `Password is expired.:<USER>`, en 5,4 s (incluye handshake TLS y la primera resolución de puertos).
- `as400.changePassword(viejaChar[], nuevaChar[])` con una contraseña generada de 16 caracteres (mayúsculas, minúsculas y dígitos, sin repetidos ni dígitos adyacentes) → **aceptada al primer intento**. PUB400 usa QPWDLVL 2/3 (admite largo > 10 y minúsculas). No hizo falta el respaldo de 10 caracteres.
- La contraseña fue cambiada y está en `function/local.settings.json` (permisos 600; el archivo se reescribió con Jackson, sigue siendo JSON válido y conserva todas las claves). El programa guarda primero la candidata como `AS400_PASSWORD_PENDIENTE` antes de llamar a `changePassword`, para no perderla si el proceso muere a mitad; al terminar la mueve a `AS400_PASSWORD` y borra la pendiente.
- Re-signon TLS con la nueva: OK en 1,2 s. Signon en claro (8476): OK en 0,6 s. Nueva fecha de expiración: 2027-10-09 (vencimiento anual).
- Servidor: **IBM i 7.5** (`VRM V7R5M0`; `SYSIBMADM.ENV_SYS_INFO`: OS_NAME=IBM i, OS_VERSION=7, OS_RELEASE=5, HOST_NAME=WWW.PUB400.COM). `CURRENT SERVER` = PUB400.

Importante: el JDBC **no** sirve para cambiar una contraseña expirada (falla el login). El perfil de servicio del Banco tiene que tener contraseña que no expire (`PWDEXPITV(*NOMAX)`) o un proceso de rotación con `changePassword` + Key Vault.

## TLS

`secure=true` (9471) funciona **sin configurar truststore**: el certificado de PUB400 lo valida el truststore por defecto del JDK. `secure=false` (8471) también funciona; ninguno de los dos dio error. En el Banco el certificado del IBM i casi seguro lo emite una CA interna: hay que agregarla al truststore de la Function (o `javax.net.ssl.trustStore` apuntando a un JKS/PKCS12 en el despliegue). Esto es lo único de TLS que este spike no puede probar.

## Driver

`AS400JDBCDriver` 14.4 / `JTOpen 21.0.7 codebase 5770-SS1 V7R6M0.00 built=2026-07-31`. Producto informado: `DB2 UDB for AS/400 07.05.0000 V7R5m0`.

## Consultas

- `SELECT CURRENT SERVER, CURRENT USER, CURRENT TIMESTAMP FROM SYSIBM.SYSDUMMY1` → PUB400 / `<USER>` / timestamp. OK.
- `SELECT COUNT(*) FROM QSYS2.SYSTABLES WHERE TABLE_SCHEMA = 'QSYS2'` → 286.
- `SELECT TABLE_NAME FROM QSYS2.SYSTABLES WHERE TABLE_SCHEMA = ? FETCH FIRST 3 ROWS ONLY` con `'QSYS2'` → `SYSTEXTSERVERS, SYSTEXTSERVERHISTORY, SYSTEXTINDEXES`. **PreparedStatement con `?` y `naming=sql` funciona**, misma forma que `AS400_SQL_CLIENTE`.

## Latencias (ms, RTT ~112 ms)

| Medición | secure=true (9471) | secure=false (8471) |
|---|---|---|
| Conexión 1 (signon + job QZDASOINIT) | 3644 | 3566 |
| Primera consulta (SYSDUMMY1) | 527 | 639 |
| COUNT(*) SYSTABLES | 524 | 448 |
| 20 consultas, misma PreparedStatement reusada, conexión 1 (prom / min / max) | 125.6 / 117 / 176 | 112.2 / 107 / 136 |
| 20 × prepare+bind+execute+close parametrizada, conexión 1 (prom) | 748.7 | 697.9 |
| Conexión 2, con la 1 abierta | 3193 | 853 |
| Primera consulta conexión 2 | 847 | 709 |
| 20 consultas reusadas, conexión 2 (prom / min / max) | 115.7 / 112 / 126 | 139.7 / 116 / 452 |
| 20 × prepare+execute, conexión 2 (prom) | 893.3 | 726.7 |
| Ciclo conectar+consultar+cerrar ×5 (patrón actual del adaptador) | 3650, 3919, 5690, 4706, 4592 → **4511 prom** | 4439, 2021, 1663, 1720, 1724 → **2313 prom** |

Lectura:

1. **Conectar cuesta ~30 RTT** (TLS: 3,2–5,7 s aquí). Una consulta con la sentencia ya preparada cuesta **1 RTT** (~115 ms ≈ el ping). TLS agrega poco por consulta pero mucho por conexión (handshakes en signon y database).
2. **Preparar cuesta ~6 RTT** (prepare + describe + open + fetch + close en viajes separados). Reusar la `PreparedStatement` sobre una conexión abierta baja de ~750 ms a ~120 ms. Hay que medir en el Banco si `extended dynamic=true` + `package=...` (paquetes SQL en el servidor) o el caché de sentencias del pool lo bajan.
3. La segunda conexión en claro bajó a 0,85 s y los ciclos en claro a ~1,7 s; en TLS se mantuvo en 3–5 s. Hay variación por carga de PUB400 (máquina compartida), pero la tendencia es clara: **TLS + login es lo caro, y se paga en cada conexión nueva**.
4. Escalado al Banco: si el RTT Function↔IBM i es ~2–5 ms (VNet + ExpressRoute/VPN), conectar con TLS rondaría 100–300 ms más el arranque del job del servidor, y una consulta reusada unos pocos ms. Aun así, conectar sigue siendo el costo dominante.

## Decisión de pooling (recomendación)

**Sí pool.** Abrir una conexión por invocación (lo que hace hoy `ResolutorClienteJt400`) cuesta aquí 4,5 s con TLS contra ~120 ms de una consulta en conexión abierta. Opciones:

| Opción | Pro | Contra |
|---|---|---|
| `AS400JDBCConnectionPoolDataSource` + `AS400JDBCConnectionPool` (jt400 nativo) | Sin dependencias nuevas; conoce las propiedades de jt400 | API vieja, menos métricas, mantenimiento de conexiones idle más tosco |
| HikariCP con `AS400JDBCDataSource` | Estándar, validación/keepalive, métricas, `maxLifetime` | Una dependencia más; hay que poner `connectionTestQuery` (`VALUES 1`) |
| Sin pool, una conexión estática perezosa por instancia | Mínimo código | Hay que manejar reconexión a mano; no escala con concurrencia por instancia |

Recomendado: **HikariCP, pool chico (2–4 por instancia), `minimumIdle` 1, `maxLifetime` < timeout de inactividad del job QZDASOINIT / firewall del Banco**, sentencia de cliente preparada una vez por conexión (o `extended dynamic=true` + `package cache=true` de jt400, a medir). En Flex Consumption cada instancia tiene su pool; el arranque en frío paga una conexión (~segundos), las invocaciones calientes no.

## Qué queda para el Banco

1. **Red**: abrir desde la subred de integración VNet de la Function hacia el IBM i los puertos **9471 (database TLS) y 9476 (signon TLS)**; 449 (svrmap) solo si no se fijan puertos; 8471/8476 únicamente si TLS no está disponible (no recomendado). Probar con `nc -zv` desde la Function (consola Kudu/SSH o una función de diagnóstico).
2. **TLS**: certificado del servidor IBM i (DCM) y su CA en el truststore de la Function.
3. **Perfil de servicio**: perfil dedicado, solo lectura sobre la(s) biblioteca(s) del cliente, `PWDEXPITV(*NOMAX)` o rotación definida, `INLMNU(*SIGNOFF)`, sin autoridad especial. Considerar el límite de intentos fallidos (QMAXSIGN): un secreto equivocado en Key Vault puede deshabilitar el perfil con los reintentos de la Function.
4. **Key Vault**: `AS400_PASSWORD` como referencia de Key Vault en app settings (identidad administrada); nunca en el repo.
5. **Consultas reales**: el usuario las provee; reemplazar `AS400_SQL_CLIENTE` (hoy placeholder `BIBLIOTECA.CLIENTES`). Confirmar si las columnas son CHAR (el adaptador ya recorta) y si hace falta `libraries=` o nombres calificados (con `naming=sql` se califica con `.`).
6. **Pool**: implementar según la tabla anterior y re-medir conexión y consulta desde la Function real en el Banco.
7. **CCSID**: no se probó con datos con acentos/ñ; validar con una tabla real del cliente (propiedad `translate binary` si hay campos `FOR BIT DATA`).
